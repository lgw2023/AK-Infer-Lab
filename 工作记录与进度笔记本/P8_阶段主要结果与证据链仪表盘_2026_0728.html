P8 DeepSeek-V4-Flash 分层推理原型的阶段性实验研究

本阶段研究围绕一个可检验的问题展开：在固定的软件栈、模型、并行配置和单次 runtime lifecycle 内，能否将注意力 KV 状态从 NPU HBM 迁移至 CPU DRAM， 随后由共享前缀请求重新命中并完整恢复至 HBM，并让模型继续生成。研究先建立 请求级观测能力和 Prefix Cache 对照，再测定可接受的 pinned-host 容量，最后 通过完整原始轨迹重放验证 D2H store、logical CPU hit、H2D restore 与 64-token decode completion 的连续机制链。

摘要

研究目的。本研究评估 DeepSeek-V4-Flash W8A8-MTP 在 8×Ascend 910B1、TP8+EP 环境中的分层状态管理可行性，重点考察 CPU DRAM 是否能够作为 KV cache 的 warm tier，以及外移后的 KV 状态能否由后续请求 可靠恢复。

方法与结果。实验采用逐级收敛设计。P8.0–P8.1 首先确认 13 项 source capability，并以 6 条 4K–131K 请求验证 request、MTP 与 prefix counter 的同 session 对齐。K0 采用 6 组顺序平衡的 64K matched pairs，比对 Prefix Cache On/Off；On 条件下 6/6 请求均命中 49,152 tokens， 平均 TTFT 由 6,542.85 ms 降至 1,739.29 ms，但该时延结果仅作描述性参考。 K1A 随后将最初不可分配的 32 GiB/rank 方案收缩为 128 blocks/rank（430,604,288 bytes/rank）的八 rank 可接受容量，并在 单 lifecycle 内观测到 4,386,781,184 bytes D2H 与 1,076,510,720 bytes H2D 传输。R17 对 20 个原始轨迹文件中的 1,369 个事件 进行完整重放，确认 8/8 D2H 与 8/8 H2D worker 均经过 submitted、copy、 poll 和 completed 终态，且 async failure 为 0。完成恢复的同一请求随后进入 decode-like 执行步骤，生成并流式返回 64 tokens。

结论。在冻结实验条件下，CPU DRAM 作为 KV warm tier 的 store/restore 机制以及恢复后继续 decode 已经获得请求、驻留、逻辑命中、 异步拷贝和输出完成五类相互一致的证据。 该结论证明机制可达，不等同于性能收益、最大容量、生产可用性或跨版本泛化。 P8.3 的 checkpoint inventory 已完整守恒，但 TP4 runtime residency budget 仍缺少 materialized bytes、hotness 与 placement A/B 数据。

研究概述：从可观测性到 KV warm-tier 机制验证

Introduction & contribution

研究背景与核心问题

大模型状态分层的关键并非“发生过一次拷贝”，而是能否证明可重用状态经历完整、可归因的迁移与恢复

DeepSeek-V4-Flash 的长上下文推理同时受到 HBM 容量、Prefix Cache 复用和异步数据搬运的约束。单独观察到 CPU 驻留、prefix hit 或 H2D 字节量， 都不足以证明 CPU DRAM 已经构成有效的 KV warm tier：CPU 驻留可能是请求结束后的 残留状态，prefix hit 可能来自 HBM 内缓存，H2D 事件也可能与目标请求无关。因此， P8 将研究问题拆为四个相互依赖的证据层级：运行时能力是否存在，请求与 runtime counter 是否能够对齐，CPU tier 是否具有可接受的分配容量，以及同一目标 KV 状态 是否按 D2H store、logical CPU hit、load scheduling 和 H2D completion 的顺序 完成迁移。

阶段性结果表明，前三个层级已经为最后的机制判断提供了充分的实验基础。 P8.1 建立了请求级观测链；K0 证明 shared-prefix 负载确实触发预期的缓存命中； K1A-R2 将过大的容量假设收缩为八 rank 均可分配的 128 blocks/rank； R17 则在 R15 同一 formal lifecycle 的完整原始轨迹上重建出 1,369 个事件， 并确认 D2H 与 H2D 各 8 个 worker 均到达 completed 终态；对应的 restore follower 继续完成 64-token decode。五类证据相互一致，支持 “KV warm-tier store/restore 及恢复后继续生成在冻结条件下可达”这一结论。

该结论的范围是机制验证，而非系统性能定论。K0 的 TTFT 和 E2EL 差异来自 Prefix Cache On/Off 的描述性对照，不是 CPU offload 的性能 A/B；R17 的 1.003 GiB H2D 证明数据发生了回迁，却没有给出回迁对端到端时延、吞吐或 HBM headroom 的净效应。与此同时，P8.3 仅完成 checkpoint 资产计量和 taxonomy 守恒，尚不足以判断 TP4 expert residency 的运行可行性。

阶段性结论。 P8 已完成 KV warm-tier 的机制级证据闭环，并形成可复用的观测与容量基线； 性能收益、External KV 路径和 expert/TP4 runtime budget 仍属于独立研究问题。

研究设计与实验条件

模型、软件版本、并行方式、请求结构和容量均被冻结，以限制跨轮诊断中的混杂因素。

Methods

研究设计

采用递进式机制验证，而不是将所有变量压入一次性能测试

研究对象为 DeepSeek-V4-Flash W8A8-MTP，运行于 8×Ascend 910B1， 采用 TP8 与 Expert Parallel。软件环境固定为 vLLM 0.22.1 （commit 0decac0）、vLLM-Ascend 0.22.1rc1（commit 5f6faa0）、 CANN 9.0.0 以及 PyTorch/torch-npu 2.10.0。冻结版本的目的不是宣称该组合 代表所有部署环境，而是保证同一机制问题在连续诊断轮中具有可比的代码语义。

实验按证据强度分为三类。第一类是 P8.0–P8.1 的 observe-only 观测实验，只验证 source capability、请求正确性和 counter 对齐，不解释性能。 第二类是 K0 的顺序平衡 matched-pair 对照，仅改变 Prefix Cache 开关， 用于验证共享前缀的命中行为，并报告描述性时延。第三类是 K1A 的机制诊断： 先测定 pinned-host allocator envelope，再构造 target prime、in-flight pressure 和 restore follower，使目标 KV 状态在一个 formal lifecycle 内经历 GPU 驱逐、CPU 命中和 H2D 恢复。R17 没有再次启动 NPU，而是对 R15 已冻结的 双轨迹文件族进行只读重放，以排除 R16 source selector 不完整造成的观测偏差。

K1A 的 accepted capacity 固定为每 rank 128 个 CPU blocks，即 430,604,288 bytes/rank，八 rank 合计 3,444,834,304 bytes。每个 base block 对应 128 tokens，44 个 unique KV tensors 合计 3,364,096 bytes/block。 目标请求采用 32K shared prefix，其中 restore 预期匹配 16,384 tokens； pressure 请求在 36,800 tokens 的 request-local progress 条件下触发并有意中止， 以保留 CPU-only 窗口，再在 engine idle 和 post-abort gate 通过后发送 restore follower。

主要判定问题。 只有当目标 KV 的物理驻留、logical CPU hit、load scheduling 和同 worker async completion 能够在同一证据链中对齐时，才接受 H2D restore 机制成立。 单独的 prefix counter、CPU-only snapshot 或传输字节量均不满足这一判据。

Methods & observational results

P8.0–P8.1 / 观测研究

在讨论 offload 机制之前，首先验证每条请求是否能与 MTP 活动、Prefix Cache proxy 和 runtime object 建立可重放对应

实验设置。P8.0 在固定 vLLM 与 vLLM-Ascend tag 上审计 13 项运行时能力，其中 7 项属于 available-but-uninstrumented，6 项已有 instrumentation；没有能力被误报为 unsupported。随后使用离线 tracer fixture 验证 schema、registry、policy、replay 和 bundle 生成链。该 fixture 包含 8 个事件和 2 个对象，产生 5 次符合预期的 no-op decision、2 条显式 warning，validation error 为 0。warning 对应无法唯一归因的 bytes，系统保留 unknown 状态而不猜测填值。

请求矩阵。P8.1-R1 在单一 session 中按顺序发送 6 条请求： 4,096-token isolated A、65,536-token shared prime、65,536-token shared follower、131,072-token isolated A、4,096-token isolated B 和 131,072-token isolated B。每条请求均要求生成 64 tokens。shared follower 与 prime 共享 49,152 tokens 的冻结前缀，其余请求不设计复用，因此 expected prefix hits 分别为 49,152 和 0。

观测结果。6 条请求全部返回 HTTP 200，prompt token 与 streamed/generated token 数均符合合同，finish reason 均为 length。MTP 的 num_draft_tokens、num_accepted_tokens 和 num_drafts 在每条请求上均增加 32，且累计计数从 0 连续增长到 192。shared follower 的 prefix hit 恰为 49,152，而 prime 和 4 条 isolated 请求均为 0。请求与 runtime object 的 join 已完成，前后 queue 状态均为 running=0、waiting=0；设备号和 rank identity 在当前 trace 中不可用，因此没有构造虚假的 device-level join。

解释。这些结果说明观测链能够区分“有意设计的复用请求”和 “应保持零命中的隔离请求”，并能将 MTP counter 增量归属到单个 request slot。 因而，后续 K0/K1A 使用的 prefix hit 和 request-local progress 不是孤立的全局 累计值。与此同时，本实验没有采集物理 KV object bytes，也没有形成 device/rank 级 identity，所以结论限于请求正确性、事件顺序和 counter continuity。

Prefix Cache 对照与 frozen-stack 兼容性审查

Controlled baseline & compatibility

P8.2-K0 / 对照实验

共享前缀命中显著缩短首 token 等待，但该基线回答的是 Prefix Cache 行为，而不是 CPU offload 性能

实验设置。K0 在三个 lifecycle 中完成 20 条成功请求，包括 4 条 warmup、4 条 prime 和 12 条 measured request。12 条 measured request 被组成 6 组 64K exact-reuse matched pairs，每组只改变 Prefix Cache On/Off 一个启动开关；请求 body 配对、server argv 单变量约束和 On/Off 执行顺序均通过 精确审计。所有请求均满足 HTTP 200、输入/输出 token 数、MTP activity、queue health 和 finish reason 合同。

缓存命中结果。Prefix Cache On 条件下，6 条 measured follower 均命中 49,152 tokens；Off 条件下全部为 0，warmup 和 prime 请求也没有 非预期命中。由此可知，该工作负载确实在 On 条件触发冻结的共享前缀复用，而 Off 条件构成有效 control。这个结果为后续 restore follower 的 logical match 设计提供了经验基线。

P8.2-K1A / 实验设计与主要结果

在单一真实模型生命周期内，对同一批 KV 状态实施“生成—卸载—命中—恢复—继续生成”的顺序验证

研究目的。本实验检验大模型推理过程中已经生成的 KV Cache 是否能够从 NPU HBM 迁移至 CPU DRAM，并在后续共享前缀请求到来时重新被识别、 调度回 HBM，继而支持该请求继续生成新 token。KV Cache 是模型为已经读过的 上下文保存的注意力中间状态；复用这些状态可以避免重新计算相同前缀。为使数据迁移 与模型请求之间具有明确对应关系，实验直接从真实 target prime 请求 产生的 KV 状态中捕获可追踪的物理 key 与逻辑前缀。

实验条件。研究对象为 DeepSeek-V4-Flash W8A8-MTP， 运行于 8×Ascend 910B1，采用 TP8 与 Expert Parallel。软件环境固定为 vLLM 0.22.1、vLLM-Ascend 0.22.1rc1、CANN 9.0.0 和 PyTorch/torch-npu 2.10.0。CPU warm tier 容量固定为每 rank 128 blocks， 即 430,604,288 bytes/rank；八 rank 合计 3,444,834,304 bytes。 一个 lifecycle 内依次执行 warmup、32,768-token target prime、 36,800-token pressure 和 32,768-token restore follower 四个请求角色。

实验过程。Target prime 首先产生真实 KV Cache， 并形成 40 个可归因的 physical target keys。随后，pressure 请求推动目标状态 离开 HBM；轨迹记录到目标 KV 的 CPU-only 驻留窗口以及 D2H store 完成。 在引擎恢复空闲后，restore follower 携带相同共享前缀到达， 对 CPU tier 产生 16,384-token 的精确逻辑命中。调度器为这些状态分配新的 HBM 槽位，compress-aware pairing 构造 40 对 CPU/HBM block 映射， 并将请求加入 _reqs_to_load。

主要结果。D2H 方向的八个 worker 全部完成，累计记录 4,386,781,184 bytes（4.086 GiB）；恢复阶段的八个 H2D worker 同样全部完成， 累计搬运 1,076,510,720 bytes（1.003 GiB），异步拷贝失败数为 0。 恢复请求的执行序列以 delayed_external_prefill 开始，随后观测到 15 个 decode_like 步骤。最终，该请求以 HTTP 200 返回， generated token count 与 streamed token count 均为 64， finish_reason=length。其首 token 时延为 1,887.16 ms， 端到端时延为 14,732.70 ms。

结果解释。上述观测构成同一恢复请求内部的连续证据： CPU DRAM 中的前缀被识别为可复用状态，load scheduling 将其送入 H2D 队列，八个 worker 完成向 HBM 的数据恢复，模型执行随后从恢复性 prefill 过渡到 decode，并完成 64-token 输出。因此，P8 已经实测完成了真实推理 KV Cache 的 HBM→CPU DRAM→HBM 往返路径，以及恢复后继续 decode 的执行闭环。

综合讨论、研究意义与局限性

机制证据的内部一致性已经形成，但样本规模、对照设计和运行时覆盖限制了外部推断。

Discussion & limitations

综合讨论

P8 的主要贡献是建立“状态身份—驻留—调度—完成”的证据方法，并据此验证 KV warm tier 的机制可达性

主要发现。本阶段最强结论来自 K1A-R17：在固定模型、TP8 并行、accepted CPU capacity 和单 lifecycle 条件下，目标 KV 状态先从 HBM 写入 CPU DRAM，随后被 restore follower 以 16,384-token logical hit 命中， 进入 _reqs_to_load，并由八个 H2D worker 全部完成回迁。 同一 restore follower 随后出现 decode-like 执行步骤，并生成、流式返回 64 tokens。该链同时具有 physical key、logical hash block、request role、 load step、same-worker completion 和模型输出证据，因而比单一 prefix counter 或传输总字节更能排除替代解释。

方法学意义。R1–R17 表明，大模型分层状态实验容易受到三类 观测错误影响。第一类是时间点错位，例如 mid-request CPU-only window 与 post-request endpoint target-loss 并不矛盾。第二类是几何错位，例如 128 个 logical hash blocks 不能直接解释为每个 FA group 都有 128 个 physical keys。 第三类是事件源不完整，例如 R16 只读取 residency family，遗漏 async-transfer family 后错误否定 completion。将请求本地进度、状态身份和完整事件源写入实验 合同，是本阶段可复用的方法贡献。

与性能结果的关系。K0 的数据表明 shared-prefix hit 与 TTFT/E2EL 的明显降低同时出现，而 TPOT 基本不变。这为 prefill reuse 的 行为合理性提供了描述性支持，但 K0 没有启用 CPU offload，R17 又没有设置 offload On/Off 对照。因此，两组结果不能拼接成“CPU warm tier 提升性能”的 因果论证。要回答该问题，需要在同一 connector、相同请求体和相同容量下进行 多 lifecycle 的随机化或顺序平衡 A/B，并同时报告 HBM headroom、TTFT、E2EL、 TPOT、throughput 和迁移重叠率。

局限性。R17 重放的是 R15 单个 formal lifecycle，证明了 已有样本中的机制闭合，但没有独立重复实验，也没有估计失败率或置信区间。 128 blocks/rank 只是四个 allocator 测试点中的最高 clean point，不代表上限。 compress-aware repair 的必要性在当前模型与版本中得到证据，但尚未跨模型或跨 vLLM 版本验证。P8.3 使用 checkpoint logical bytes，未观测 TP4 materialized footprint 和 runtime hotness。上述限制共同决定了当前结论应表述为 instrumented-path mechanism evidence，而非 production readiness。

当前证据支持 ACCEPTED
  • 固定 vLLM/vLLM-Ascend tag 的 13 项 capability 有本地 source evidence。
  • selected workload 的 observe-only request/MTP/prefix proxy trace 可对齐。
  • Prefix Cache On/Off 控制、body pairing 与 order balance 精确成立。
  • 每 rank 128 blocks / 430,604,288 bytes 的八 rank pinned envelope 成立。
  • SimpleCPUOffload 的 D2H store 与 H2D restore 在单 lifecycle 内真实发生。
  • exact 16K logical CPU hit 经 `_reqs_to_load` 进入 H2D，并完成 8 worker copy。
  • checkpoint inventory/taxonomy 在文件级 provenance 与 bytes 守恒上成立。
当前证据不支持 NOT CLAIMED
  • K1A offload 对 TTFT、TPOT、throughput、HBM headroom 有正收益。
  • R13 的 compress geometry mismatch 是所有模型/版本的唯一根因。
  • accepted 128 blocks 是最大容量，或扩大容量一定更优。
  • R17 机制闭环自动授权 UCM / External KV / SSD cold tier。
  • checkpoint 279.399 GiB 等于 TP4 runtime materialized footprint。
  • 已有 per-expert hotness、reuse distance、static placement A/B 或 miss penalty。
  • 四卡 full-model expert-residency 已达到 path_smoke 或 production readiness。
讨论结论。 当前证据足以支持冻结边界内的 KV warm-tier 机制结论，并支持将完整轨迹源、 request-local progress 与 same-worker completion 作为后续实验的固定方法； 性能、可靠性、容量上限和跨环境泛化仍需新的对照与重复实验。

Future work

研究议程

下一阶段应从“机制在一个实现中成立”推进到“机制可迁移、收益可量化、expert 预算可计算”

第一优先级：External KV 路径复现。K2-R0 以 UCM DRAM-first connector 为独立研究对象，保持 DeepSeek-V4-Flash、TP8+EP+MTP 和 32K prime/follower 请求不变，验证 save、external DRAM hit、 Cache load/H2D 和 completion。该实验的主要终点仍是路径与完成语义， 延迟只作描述性记录。若 K2 能在不同 connector 上重现同类证据链，将提高 KV warm-tier 结论的实现可迁移性；若失败，则应首先区分接口、keyspace 和 async source 的差异，而不是直接归因于硬件。

第二优先级：受控性能 A/B。在 connector 机制稳定后， 应设计多 lifecycle、顺序平衡的 offload On/Off 实验。控制模型、请求 body、 context、output tokens、并发度、CPU capacity 与 keep-alive 状态，联合报告 TTFT、E2EL、TPOT、throughput、D2H/H2D bytes、copy/compute overlap 和 HBM headroom。只有此类数据才能判断 warm tier 的净收益及其适用负载区间。

第三优先级：Expert/TP4 runtime budget。P8.3-I1 应先采集 per-expert invocation frequency、reuse distance、load bytes、resident lifetime 和 miss penalty，再结合 TP4 ownership 计算 non-expert/shared 常驻项、hot expert cache、双 staging buffer、KV pool、graph/workspace、 collective buffer 与 fragmentation reserve。完成这些量之后，P8.4–P8.6 的 placement simulation、static/EPLB A/B 和真实 mover 才具有可解释输入。

三条路线必须保持独立授权和独立 lifecycle。K1A 的 GREEN 不能自动解锁 K2、P8.3-I1 或后续 mover；反之，checkpoint inventory 的完整性也不能作为 KV connector 性能的旁证。每轮更新应保留任务 ID、冻结条件、样本量、绝对值、 formal grade、claim boundary 和原始证据路径。
