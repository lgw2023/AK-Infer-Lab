4. P6.3A 关闭 matched MTP on/off 机制对照门；8/8 cells、48/48 measured batches、108/108 measured requests 全部成功，24/24 paired batches 的 MTP-on TPOT/E2EL 更低且 batch throughput 更高。
5. P6.3B-R4-R1 关闭显式 Prefix Cache control 机制门；64/64 request 成功，off hit=0，on primary 9/9 正命中并严格符合 16K hybrid LCM floor。

   接受 `mechanism_confirmed_tradeoff_only`。

必然失败，已以 `blocked_p6_3c_not_strict_single_variable` 保留且不创建原配置 executable workload。独立 P6.3C-R1 已完成首次实机，但在 KV-cache 初始化阶段停止，未进入 scheduler；容量校准后的 P6.3C-R2 run01 又在 vLLM 启动前的 task-local overlay 准备阶段停止，未形成容量、调度或性能证据，且资源恢复 clean。后续 F1–F3 分别关闭运行时布局、loopback 传输、scheduler 共到达与 request-ID 识别问题；F4 最终形成受控调度机制证据，A1 已完成零 NPU 来源与分类再归档。P6.3A 的 green 接受的是冻结 fixed-order matched workload

## 6. P6.3 计划复审结论

P5→P6→P7→P8→P9 的总路线不变，但原先把 Prefix Cache、MTP、Chunked Prefill、
`max_num_seqs`、`max_model_len` 平铺为五项同级 A/B 不够严谨。建议改为以下顺序。

### P6.3A：matched MTP on/off（第一优先级）

现有 no-MTP control 是修复前 degraded cell，不能与 P6.1 MTP matrix 直接形成严格 A/B。
P6.3A 已在同一 runtime、body、warmup、cell 和非目标开关下只改变 MTP。执行合同扩展为
8 个 cell，覆盖 `4096/65536/131072`、`64/256` output 与 c1/c4/c8；每 mode 每 cell 3 个
measured batch，合计 48 batch/108 request。开发机已接受为 `green_p6_3a_mtp_matched_ab`；
用户性能以 unprofiled run 为准，若需要 operator 归因则另起 profiled 跟进。

### P6.3B：Prefix Cache on/off（第二优先级）

P6.1 的 canonical bodies 有意降低公共前缀，不能拿来验证 Prefix Cache 收益。P6.3B 使用
purpose-built repeated-prefix bodies，固定共享前缀长度/比例、请求顺序、复用距离、输出和并发，
只改变 Prefix Cache 开关。合同覆盖 `4096/32768/65536/131072 × 50%/90%` 八个 group；
每 group 每 mode 1 prime + 3 measured follower。该结果同时是 P8.2 K0 的直接输入，但不复制
Qwen 的 15-cell 结论或把 target ratio 冒充 observed hit ratio。

### P6.3C：Chunked Prefill on/off（条件项）

开发机已对 vLLM `0decac0d...` 和 vLLM-Ascend `5f6faa0c...` 做精确冻结源码审计。CLI parser
通过 `BooleanOptionalAction` 同时提供 `--enable-chunked-prefill` 和 `--no-enable-chunked-prefill`，
因而“显式双布尔”本身可满足；但 `SchedulerConfig.verify_max_model_len()` 明确拒绝
`max_num_batched_tokens < max_model_len` 且 chunking=false 的组合。将冻结值代入得 `4096 < 135168`，
因此 off 侧不能在任何请求前形成 resolved false 证据。唯一规避是把 `max_num_batched_tokens`
增至至少 135168 或把 `max_model_len` 降至最多 4096，两者都违反严格单变量合同。结论因而为
`blocked_p6_3c_not_strict_single_variable`；未创建可执行 workload、mode runner、request body 或服务器任务。

### 后移的两项

- `max_num_seqs` 是 scheduler/capacity sweep，不是简单开关 A/B。它应作为可选 P6.3D，只有在明确要回答并发/排队问题时执行，并重新定义 graph/HBM/queue 验收。
- `max_model_len` 更接近容量与 reservation 边界。official 135168 已验证后，不应作为 P6.3 必做性能 A/B；建议移入 P7 capacity boundary，除非后续提出“固定 workload 下仅改变 reservation 上限”的明确问题。

## 9. HBM 采集与干扰设计复审

### 9.1 结论

2026-07-15 对外部技术对话《HBM 采集与干扰设计》完成项目内复审。该对话对后续合同设计有
较高价值，但属于待验证的技术输入，不是本项目服务器事实。它不撤销 P6.1C-R1；已完成的
P6.3A 全程禁用 profiler/HBM sampler，因而没有把该采集变量引入 matched MTP on/off 对照。

P6.1C-R1 的 `green_mtp_official_context_ladder` 保留，但其中“容量”只表示冻结配置下
`131072+64+c1` 请求成功且未见请求、健康、queue、MTP counter 或 cleanup 失败；它不表示
KV pool 剩余 token/block 数、逻辑 KV headroom 或物理 HBM 安全余量已经被完整量化。

### 9.2 本项目已有证据

1. 原 P6.1C 确实因 `npu-smi info -t usages` 缺少 `-i` 而出现 36/36 parse failure，且
   “6 秒窗口内 20 样本 + 5% duty”不可满足；对话指出的合同矛盾与项目历史一致。
2. P6.1C-R1 的单次八卡 `npu-smi info` sweep p50/p95 为
   `1.056859569/1.071280632s`。即使选择 5 秒周期，p95 subprocess wall ratio 仍约为
   `21.4%`；该 wall ratio 不能直接等同于推理干扰，但足以说明它不适合作为短窗口高频主信号。
3. 五档 official ladder 的 per-card peak HBM 仅落在 `61436-61447 MB`；4K 档最紧张卡
   为 `61442 MB`，128K 档为 `61447 MB`，只增加 `5 MB`。这与“物理 KV pool 已在服务启动
   阶段建立、请求长度主要改变逻辑 block 使用”的解释一致，也直接证明当前 HBM trace 对
   context ladder 的信息增益很低；但该结果不能单独证明 allocation/residency/driver-reserve 的
   精确实现语义。
4. 当前干扰门只有一组 control 与 selected-validation：control=`22101.745289 ms`，
   sampled=`19542.7234 ms`，因此记录为 0 增幅。它只证明本次没有观察到回归，不能证明
   sampler 零干扰，也不足以支持统计型 10% 上界。

### 9.3 后续采用规则

1. **P6.3A 不改。** 保持 HBM sampler/profiler 禁用，避免在已冻结的性能 A/B 中引入新变量。
2. **P7 capacity boundary 改用分轴证据。** 启动时保存 KV cache token capacity 与理论最大并发；
   运行时优先检查 `vllm:kv_cache_usage_perc`、`vllm:num_preemptions`、
   `vllm:num_requests_waiting_by_reason{reason="capacity"}`、
   `vllm:request_prefill_kv_computed_tokens`、request success、health、queue 和 cleanup。
   这些指标在当前 vLLM-Ascend 0.22.1rc1 上仍需 server preflight；缺失时标记 logical-capacity
   evidence incomplete，不得伪造或由 HBM 代替。
3. **HBM 降为物理旁证。** 默认只取 server-ready、请求前、TTFT/prefill 附近、请求结束、cleanup
   后 3-5 个 event-aligned bounded snapshots；不再机械要求每个请求 20 个样本。只有新问题明确
   需要捕获短时物理峰值时，才单独做 instrumentation qualification。
4. **状态轴分离。** 后续合同分别记录 functional、logical KV capacity、physical HBM evidence、

`engine_client.generate()`；AsyncLLM 分别向 EngineCore 发送 message；EngineCore 收到第一条
后已有 scheduler work，若第二条尚未进入 input queue 就立即 step。Chunked Prefill Off
“整段不超过剩余预算才准入”和 On“裁到剩余预算”的差异只对已经在 waiting 的请求生效。
因此 F2 的准确结论是：运行时布局和 loopback 传输均已修复，但该 HTTP 请求形态没有制造
同轮预算竞争，故没有产生 Chunked Prefill 机制辨识证据。F2 性能轨道的两组 order-balanced
差异也不复现同一方向，且机制未触发，不能归因为 Chunked Prefill。

下一条独立链是 `P6.3C-R2-F3 atomic-pair-admission matched A/B`。它保持
12288/12288/2、三 cell、六 lifecycle、90 request、48 batch、Prefix=false、共同 repair、
MTP/graph/block/model/quantization 与 Off→On→On→Off 全部不变，并在两侧共同安装
task-local EngineCore 准入层：

- 仅识别 `p6_3c_r2_f3` measured pair；warmup 与普通请求原样进入原 `add_request`；
- 首个 pair member 在调用 `scheduler.add_request` 前缓冲，因此不会让 EngineCore 提前
  进入 step；第二个到达后按 pair index 0→1 连续调用原 `add_request`，随后才允许下一轮
  scheduler；
- 30 秒 peer timeout、客户端 abort 和 shutdown 都有显式清理与事件证据，任何 unmatched、
  duplicate、timeout、abort 或 release failure 均不能形成 candidate；
- 机制轨道不只查 partial prefill，还要求每个 cell 首个相关 step 的
  `waiting_order_before` 精确为两个 request ID。4K+4K 两侧首轮应为 4096+4096；
  10K+6K Off/On 应分别为 10240+0 与 10240+2048；8K+8K 应分别为
  8192+0 与 8192+4096；
- 性能轨道仍关闭 scheduler observer 与 profiler；共同准入层只留下必要 release/wait
  审计，屏障等待开销单列，所有时延和吞吐仍只作受控 co-arrival 环境内描述。

F3 回答的是 Chunked Prefill 在“确定同时可见”的冻结调度压力下是否改变 scheduler，
不是自然生产 OpenAI API 流量的性能承诺。服务器结果经开发机验收前，第 11 页仍不得把
Chunked Prefill 列为已完成正向成果。

R2-F3 已在 `main@28937477` 的服务器完成六个 lifecycle：90/90 engine request、
48/48 batched HTTP call、六次 vLLM ready、共同 overlay/repair、零 retry、0–7
keep-alive 精确恢复和全局清理均通过，Off/On argv 仍只差显式 Chunked Prefill 开关。
但 controller 虽安装成功，42 个 measured pair 均未出现 buffered/released 事件，
六个机制首轮合同也均未成立。直接证据显示 vLLM 内部请求 ID 会在规范 member index
之后追加 8 位十六进制运行时后缀，例如
`cmpl-p6_3c_r2_f3_mechanism_no_pressure_4k_4k_r01-0-a19f074f`；F3 parser 只接受
末尾直接为 `-0` / `-1`，所以所有请求绕过准入层。F3 finalizer 也用无后缀 ID 对 release、
waiting 和 scheduled map 做 exact equality；这两个缺陷必须在同一链修复。F3 的性能数据
没有建立受控 co-arrival，不能回答目标机制问题，也不能写成 Chunked Prefill 负结论。

下一条独立链为 `P6.3C-R2-F4 request-id-normalized atomic co-arrival`。它不重跑或覆盖
F3，并保持所有科学参数、请求体、cell、生命周期、执行顺序和计数不变。新链只做两侧共同

- 严格识别 `cmpl-<F4 canonical pair>-<0|1>-<8 hex>`，同时保留 actual ID、canonical
  member ID、pair key、member index 与运行时后缀；错误前缀、错误 index、缺失或非 hex
  后缀均不得进入 barrier；

- 每次 pair 状态变化后写持久 controller-state checkpoint。生命周期终态优先使用 shutdown
  事件；若进程正常清理但 callback trace 缺失，可用最后一个完成全部 expected pair、
  `pending=0`、`failed=0` 的 post-release checkpoint，且必须仍满足 42/42 exact release、
  零 failure event和全局 clean。

F4 只支持共同受控 co-arrival 环境内的机制辨识与描述性性能结果；开发机现已接收其
scheduler mechanism 证据，第 11 页可以将 Chunked Prefill 写入“机制已观察到”，但必须
同时写明固定性能样本未显示收益，且不得写成生产流量下的正向优化成果。
