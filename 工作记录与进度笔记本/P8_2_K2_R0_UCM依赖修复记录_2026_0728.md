# P8.2-K2-R0 UCM 依赖修复记录（2026-07-28）

## 2026-07-29 run03 归因与 run04 定向修复

run03 的零 NPU 完整日志归因已完成，正式 grade 为
`attributed_p8_2_k2_r0_run03_fawa_startup_failure`。精确首错不是 NFS、依赖、
CacheStore DRAM buffer 或请求路径，而是 scheduler FA PosixStore 的 GC 几何：

```text
posix_capacity_gb(16) is too small, GC cannot recycle any files.
Minimum recommended: 183GB
```

这里的 “cannot recycle” 表示默认 `data_dir_shard_bytes=3` 形成 4096 个目录分片后，
每个分片按 `0.7 trigger × 0.1 recycle` 的整数截断得到 0 个回收文件；不表示现场已经
存在无法删除的旧文件。run03 同时给出 worker 实测块大小：FA=`3186688 bytes`，
WA=`6627328 bytes`。FA/WA 存储路径已经由 pinned UCM 自动命名为 `fawa_fa` /
`fawa_wa`，不需要再做一次 namespace 修复。

run04 已实现 split-aware 修复和停卡前 exact preflight：

- `data_dir_shard_bytes=2`，目录分片从 4096 降到 256；
- YAML 总 `posix_capacity_gb=64`，经 pinned
  `UCMFAWAConnector` 整数对半后，FA/WA 各 32 GiB；
- 同一源码公式下，FA 最低 12 GiB、实际每分片回收数 2；WA 最低 24 GiB、实际
  每分片回收数 1；
- 父 attribution manifest 与全部 payload、FA/WA 唯一 worker block size、两套
  CacheStore buffer 门、`/dev/shm`、MemAvailable 和 storage free space 均在 NPU
  触碰前自动验证；
- 只授权一个 TP8 lifecycle，固定 warmup→prime→follower 三请求、零 retry。若服务
  ready，则继续原始目标 `save → external lookup/hit → Cache load/H2D → follower
  completion`，而不是只把启动变绿。
