P6.3B Provenance：最终 GREEN 不覆盖中间 yellow / red / blocked 的工程事实

从 zero-hit 到 explicit Prefix Cache matched A/B 的完整修复链
YELLOW ORIGINAL P6.3B64/64 but zero hit

query positive，hit delta 全为 0；不能接受机制效应。

RED R1Import order

sitecustomize eager import 固结基类 spec key；0/12 request。

GREEN R2Deferred repair

3 prime + 9 measured；9/9 positive hit，证明修复可达。

YELLOW R3On-vs-on

Off 侧省略 flag 继承 default=true；两侧 hit 相同。

BLOCKED R4NFS ownership

cp -a 在 root-squash 上 EPERM；0 lifecycle，0 request。

GREEN R4-R1Explicit Off / On

ownership-safe copy；64/64、Off hit=0、primary 9/9。

为什么必须保留负证据
  • zero hit 证明“query positive”不等于“机制已命中”。
  • R1 暴露 import-order 会固结 hybrid-KV spec key。
  • R3 证明省略 flag 不能代表 Prefix Cache off。
  • R4 证明 NFS root-squash 会破坏 cp -a。
R4-R1 关闭了什么
  • 显式 Prefix false / true。
  • same R2 hybrid-KV repair。
  • 跨 mode canonical bodies 字节相同。
  • 64/64 request 与 cleanup 全过。
  • 三个 primary group 9/9 exact hit。
R4-R1 没有关闭什么
  • 没有证明普遍共享前缀必然命中。
  • 没有随机化或消除固定顺序偏差。
  • 没有统计显著性分析。
  • 没有证明硬件瓶颈或通用性能收益。
  • 没有撤销历史 provenance。
治理
  • 最终 accepted grade 是 green_p6_3b_r4_r1_explicit_prefix_cache_matched_ab，但其 claim boundary 仅限 primary scope mechanism effect。
  • 把中间失败保留下来，可让后续 P8 的 Prefix、hybrid-KV、NFS copy 与 import-order 合同直接复用这些已知风险。
